# 0022 — Периодически обновлять задержку серверов

## Что требовалось

Исправить завышенное значение «пинга» в списке серверов и обновлять его раз в
несколько секунд.

## Почему

Интерфейс использовал `elapsed_ms` строгой проверки `caelo_probe`. Это время
первого HTTPS-запроса через новый userspace-туннель: в него попадают установка
WireGuard-соединения, TLS и HTTP. Такая величина доказывает работоспособность
конфига, но не соответствует ожидаемой пользователем задержке и измерялась лишь
один раз после загрузки списка.

## Как сделано

- Контракт `caelo_probe.elapsed_ms` оставлен без изменений: выбор узлов всё ещё
  опирается на полноценную холодную проверку доступности.
- Добавлен отдельный C ABI-вызов `caelo_measure_latency`. Он сначала доказывает
  работоспособность конфига, затем выполняет второй HTTPS-запрос через тот же
  туннель и возвращает его длительность в `latency_ms`.
- Каталог серверов использует только `latency_ms`, поэтому холодный handshake
  больше не показывается как задержка.
- Контроллер повторяет последовательный цикл измерений через 5 секунд после
  завершения предыдущего. Циклы не накладываются; ошибка не стирает последнее
  успешное значение; таймер отменяется при перезагрузке и уничтожении.
- Обновлены тестовые контракты и добавлен тест повторного измерения.

## Решило ли задачу

Да: в интерфейсе отображается тёплая end-to-end HTTPS-задержка через реальный
туннель, а значение обновляется каждые несколько секунд. Это по-прежнему не ICMP
echo — для WireGuard/AmneziaWG он не доказывает ни handshake, ни прохождение
пользовательского трафика — поэтому в коде и документации метрика называется
latency, а не ICMP ping.

## Проверка

- `go test ./...` — успешно, включая новые тесты разделения холодного и тёплого
  запросов.
- `flutter analyze` — замечаний нет.
- `flutter test` — 78 тестов прошли.
- `./scripts/build-android.sh debug` — собраны APK для трёх ABI и universal
  debug APK с новой native-библиотекой.
- Universal APK установлен на Android 16 emulator (API 36). Для сохранённого
  пользовательского сервера холодное значение предыдущей реализации около
  `1034 мс` сменилось тёплыми измерениями `175 мс`, затем `182 мс` и `180 мс`;
  это одновременно подтверждает новый смысл величины и её периодическое
  обновление. В раскрытом списке значения появились у нескольких сохранённых
  конфигураций.

## Откат

Изменение изолировано в ветке `36-periodic-server-latency`. Для полного отката
достаточно отменить её итоговый коммит; схема сохранённых данных не менялась.
